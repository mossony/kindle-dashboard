# Tesla battery card

The dashboard uses Fleet Telemetry and keeps the latest reported battery level in `DASHBOARD_KV`. Scheduled Fleet API cache polling is disabled (`crons = []`). Previously stored readings can still be displayed until a newer telemetry reading arrives. The battery card shows the vehicle report time.

1. Create an application in the [Tesla developer dashboard](https://developer.tesla.com/dashboard). Select Authorization Code and Machine-to-Machine. Use `https://tesla.mossony.online` as the allowed origin and `http://localhost:53682/tesla/callback` as the allowed redirect URI. Leave Allowed Returned URLs blank. Select Vehicle Information. Set a billing limit in the Tesla portal before activating the sync. [Tesla onboarding](https://developer.tesla.com/docs/fleet-api/getting-started/what-is-fleet-api)
2. The Worker serves the public key at `https://tesla.mossony.online/.well-known/appspecific/com.tesla.3p.public-key.pem`. The corresponding private key lives at `%LOCALAPPDATA%\KindleDashboard\tesla-private.pem`. Once Tesla issues the Client ID and Client Secret, exchange a partner token and register `tesla.mossony.online` with Tesla's North America Fleet API. [Partner tokens](https://developer.tesla.com/docs/fleet-api/authentication/partner-tokens) and [registration endpoint](https://developer.tesla.com/docs/fleet-api/endpoints/partner-endpoints#register)
3. Request `openid offline_access vehicle_device_data` and authorize the app in Tesla. Receive the authorization code on the local callback and exchange it using the North America audience `https://fleet-api.prd.na.vn.cloud.tesla.com`. The exchange uses the Client Secret locally. [Third-party OAuth](https://developer.tesla.com/docs/fleet-api/authentication/third-party-tokens)
4. In Cloudflare Workers, add `TESLA_CLIENT_ID`, `TESLA_VIN` (17 uppercase characters), and `TESLA_REFRESH_TOKEN` as Worker secrets. Add the refresh token last, once the other settings and billing limit are in place. The Worker saves renewed tokens in the existing private KV namespace. A replacement `TESLA_REFRESH_TOKEN` starts a new token chain if Tesla authorization needs to be renewed. Removing this secret stops future Tesla calls.

Check the Worker invocation logs for `Tesla cached data failed` if the card does not appear after a scheduled run. Tesla documents `404` when no cached data exists and `412` when the vehicle does not support this endpoint. The Worker keeps a previous reading if an update fails. [Cached vehicle data](https://developer.tesla.com/docs/fleet-api/endpoints/vehicle-endpoints#vehicle_data_cached)

The local `node scripts/connect-tesla.mjs` helper performs steps 2-4 once the public key is live. It reads `TESLA_CLIENT_ID`, `TESLA_CLIENT_SECRET`, and `TESLA_VIN` from the local process environment and requires Wrangler to be signed in. Use a local masked prompt or secret manager for the Client Secret. Set the Tesla billing limit before running the helper. Open the printed authorization URL in a browser on the same computer as the helper.

## Live telemetry on Windows

The Compose project in `telemetry/` uses Tesla's mTLS receiver, a private Redis broker and a bridge that forwards only `BatteryLevel` and `DetailedChargeState` to the Worker. Deploy the Worker and set a separate random `TESLA_TELEMETRY_TOKEN` secret. Set the matching token and `TESLA_VIN` in the ignored `telemetry/.env` file. The bridge forwards battery readings at most every five minutes and charging state changes promptly.

Supply a TLS certificate and its key as `telemetry/certs/fullchain.pem` and `telemetry/certs/privkey.pem`, then provide the issuing CA certificate in Tesla's vehicle configuration. Keep the CA private key and the separate Tesla app-signing key outside the containers. By default, `docker compose --env-file telemetry/.env -f telemetry/compose.yaml up -d --build` binds the receiver to local port 4443 only. For vehicle traffic use a separate DNS-only hostname, publish the receiver port on the selected LAN interface, and forward that single TCP port to the workstation. Tesla's client certificate must reach the receiver. Keep Windows and Docker running while the vehicle is expected to send data.

HAProxy passes encrypted TCP through to the receiver and limits connection counts and new connection rates. Only HAProxy publishes a port. Redis is on an internal Docker network and the containers run with read-only filesystems, resource limits and dropped capabilities. The bridge subscribes to one VIN and the Worker checks the VIN and its separate bearer token. Per-address connection limits use the source address visible to Docker Desktop, which may be shared after NAT. The limits protect local resources but cannot prevent traffic from saturating the home internet connection.

On BWPC, Docker Desktop starts at Windows sign-in. All Compose services have `restart: always` so Docker starts them when its engine starts, including after a manual container stop followed by an engine restart. To intentionally take the stack offline across restarts, use `docker compose --env-file telemetry/.env -p kindle-tesla -f telemetry/compose.yaml down`.

After validating the receiver from outside the home network, pair the application virtual key and configure the vehicle using Tesla's Vehicle Command proxy. Request `BatteryLevel` and `DetailedChargeState` with 60-second intervals. Confirm that the telemetry configuration is synced and check for a newer report time on the dashboard. [Tesla Fleet Telemetry](https://developer.tesla.com/docs/fleet-api/fleet-telemetry)
